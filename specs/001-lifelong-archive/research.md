## 技术决策记录

### 决策 1: 档案码技术方案

**Decision**: 采用二维码（QR Code）作为全生涯数字档案码的载体

**Rationale**:
- 二维码普及度最高，手机扫码零门槛（原生相机即可）
- 可编码足够信息（档案 ID + 校验码），成本低
- 可打印为实体卡片（胸牌/钥匙扣），适合心青年随身携带
- 已有成熟的前端生成库（qrcode.js，轻量无依赖）

**Alternatives Considered**:
- NFC 芯片：成本高、需要专用设备读取，不适合志愿者/小机构
- 短链接：依赖网络、易失效、不适合离线场景
- 条形码：信息容量不足、不够直观

**Implementation Note**: 使用 `qrcode.js` 库在前端生成，码内编码 `{HOST}/archive/{ID}?token={HMAC}` 格式的 URL

### 决策 2: 数据存储方案（当前阶段）

**Decision**: 当前版本（v1.x）保持浏览器 localStorage 存储，但数据结构按 JSON Schema 规范化，为后续服务端迁移做准备

**Rationale**:
- 现有应用是纯前端单页 HTML，localStorage 是当前唯一存储
- 数据主权机制（联邦计算、监护权转移）需要服务端，但 v1.x 阶段先做前端功能验证
- JSON Schema 规范化存储格式 → 后续迁移到 IndexedDB 或服务端 API 时，只需替换存储层

**Alternatives Considered**:
- 直接引入 IndexedDB：比 localStorage 更强大但 API 复杂，对单文件应用重构影响大
- 直接引入服务端（Node.js + SQLite）：改变部署形态，v1.x 阶段过早

**Migration Path**: localStorage → IndexedDB（v2.x）→ 服务端 API + SQLite/PostgreSQL（v3.x）

### 决策 3: 角色权限模型设计

**Decision**: 基于角色 + 授权令牌的双层权限模型

**Rationale**:
- 角色定义"能做什么"（权限模板）
- 授权令牌定义"对谁做"（绑定心青年 + 有效期）
- 两者结合实现精细的访问控制，同时保持前端可实现的简单性

**权限层级设计**:

| 角色 | 读取范围 | 写入范围 | 管理范围 | 有效期 |
|------|----------|----------|----------|--------|
| 心青年本人 | 全部（受保护字段除外） | 心情、愿望、任务确认 | 无 | 终身 |
| 家长/监护人 | 完整档案 + 跨机构历史 | 所有模块 | 监护权管理、授权管理 | 至监护权转移 |
| 机构老师 | 当前服务心青年的完整档案 | ISP、行为干预、能力评估 | 无 | 服务期内 |
| 照护者/护工 | 安全速查 + 自己录入的历史 | 饮食/排泄/服药/外出 | 无 | 雇佣期内 |
| 志愿者 | 仅安全速查页 | 活动陪伴记录 | 无 | 单次活动 |
| 政府 | 宏观趋势看板（脱敏聚合） | 无 | 无 | 永久 |

**授权令牌结构**:
```
{
  youthId: "string",
  grantorId: "string",       // 授权人（心青年本人或家长）
  granteeId: "string",        // 被授权人
  role: "enum",               // 角色类型
  scope: ["read:module-a", "write:module-b"],
  validFrom: "ISO date",
  validUntil: "ISO date | null"  // null = 永久
}
```

### 决策 4: 速读卡生成算法

**Decision**: 基于权重的信息提取 + 模板渲染

**Rationale**:
- 速读卡需要从档案中自动提取关键信息，而非手工选择
- 使用固定模板（A4 单页），按区域填充：左上=基本信息，右上=沟通方式，中部=行为红线（最多 5 条），下部=注意事项
- 行为红线的权重判定：标记为"红线"类别的记录优先，其次是近 7 天的异常记录，最后是家长设定的固定红线

**速读卡模板布局**:
```
┌─────────────────────────────────────────┐
│  [姓名]  [年龄·性别]                      │
│  ─────────────────────────────────────── │
│  沟通方式: [3-5 条要点]                    │
│  ─────────────────────────────────────── │
│  ⚠ 行为红线:                             │
│  1. [红线行为描述]                         │
│  2. [红线行为描述]                         │
│  3. ... (最多 5 条)                       │
│  ─────────────────────────────────────── │
│  急救联系人: [姓名] [电话]                 │
│  近期注意事项: [1-3 条]                    │
│  ─────────────────────────────────────── │
│  生成时间: YYYY-MM-DD  档案码: XXXX       │
└─────────────────────────────────────────┘
```

### 决策 5: 对话式采集的 AI 实现方式

**Decision**: 使用前端预设问题模板 + 关键词分类引擎

**Rationale**:
- 当前为纯前端应用，无法调用 LLM API（无后端）
- 使用"预设分类问题"模式：AI 对话本质是结构化表单的对话化包装
- 每个模块预设 3-5 个引导问题，用户自然语言回答后通过关键词匹配分类

**分类引擎逻辑**:
- 睡眠/起夜/梦话 → 照护模块
- 吃饭/饮食/喝水/食欲 → 照护模块
- 情绪/烦躁/开心/哭/笑 → 情绪与行为模块
- 吃药/医院/看病/医生 → 照护与医疗模块
- 工作/烘焙/打扫/任务 → 工作支持模块
- 喜欢的朋友/想去的地方/愿望 → 我喜欢的生活模块
- 表达困难/不听指令/特殊习惯 → 沟通说明书模块

**后续扩展**: 服务端就绪后可接入 LLM API 实现真正的 NLU 分类

### 决策 6: 政府看板脱敏聚合方案

**Decision**: 当前版本使用前端本地聚合统计（模拟），后续服务端版本实现真正的联邦计算

**Rationale**:
- 联邦计算需要服务端基础设施，当前纯前端无法实现
- v1.x 的目标是验证看板 UI 和交互，使用模拟数据展示效果
- 数据结构预留 `anonymizationLevel` 字段，后续服务端可直接替换数据源

**模拟聚合方式**: 前端遍历所有本地档案，按维度聚合统计，不暴露个体信息

### 决策 7: 文件拆分策略

**Decision**: 按模块拆分为独立 JS 文件，通过 namespace 隔离

**Rationale**:
- 当前 `app.js` 是单一巨大文件（推测），需要拆分以降低耦合
- 按功能模块拆分：auth.js、profile.js、records.js、quickcard.js、timeline.js、chatbot.js、charts.js、government.js
- 共享数据通过 `AppState` 全局状态对象管理
- 拆分原则：先拆后合，每个文件可独立维护

**目标文件结构**:
```
js/
├── app.js           // 主入口，路由和初始化
├── state.js         // AppState 全局状态管理
├── storage.js       // 数据存储层（localStorage 抽象）
├── auth.js          // 登录/注册/角色管理
├── profile.js       // 心青年档案 CRUD
├── archive-code.js  // 档案码生成与解析
├── records.js       // 记录采集（多模块）
├── quickcard.js     // 速读卡生成与打印
├── timeline.js      // 时间轴与分类检索
├── chatbot.js       // 对话式采集
├── permissions.js   // 角色权限管理
├── charts.js        // 数据可视化
├── government.js    // 政府看板（脱敏聚合）
└── utils.js         // 工具函数
```

### 决策 8: 项目结构保持单页应用

**Decision**: 不引入框架，保持原生 HTML/CSS/JS 单页应用，但引入模块化组织

**Rationale**:
- Constitution v2.0.0 原则 V 明确要求"优先使用原生 HTML/CSS/JS"
- 应用面向心智障碍服务领域，使用群体可能设备老旧、技术能力有限
- 单文件部署简单（一个 HTML + CSS + JS 文件夹即可），适合机构内部部署
- 模块化拆分后，每个 JS 文件 < 300 行，可独立维护

**Constitution Compliance**: 符合原则 V（轻量与可维护）
